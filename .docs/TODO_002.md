Ничего не менял — только изучил запуск и предложил направление.

Сейчас `./start` поднимает Docker-зависимости, а затем создаёт в tmux шесть одинаковых панелей: `make logs`, `make api`, `make cons`, `make conf`, `make write` и `make tx`. В итоге важные сигналы теряются среди повторяющихся строк, а `tx_bot` и некоторые логи печатают длинные JSON и хэши. При этом у проекта уже есть материал для хорошей живой панели: API принимает транзакции, consumer добавляет их в граф, confirmer пересчитывает веса, writer подтверждает транзакции. Сейчас эти части процесса трудно увидеть как единый поток.

## Предлагаемая концепция: L0 Live Console

**Премиальный тёмный терминал**: графитовый фон, аккуратная сетка, немного cyan для активных процессов, зелёный для успеха, янтарный для предупреждений и красный для ошибок. Визуально — скорее презентационная консоль работающей системы, чем раскрашенный вывод логов.

Вместо шести простыней — шесть панелей с разными задачами:

1. **Система** — состояния API, RabbitMQ, MongoDB, Redis и Memgraph, время работы, число перезапусков. Зависимость показывается `UP / DOWN / UNKNOWN`, а не предполагается работающей по одному только факту запуска Docker.
2. **API** — входящие запросы в секунду, ответы по классам статусов, задержка, последние события. Полные тела запросов не выводить.
3. **Consumer / ingress** — обработанные сообщения, успешное добавление в граф, отказы по причинам, скорость обработки, несколько последних коротких идентификаторов транзакций.
4. **Confirmer / DAG** — общее число узлов, сколько узлов попало в выборку и обработано, длительность цикла, число ошибок пересчёта, статистика весов обработанной выборки и порог подтверждения.
5. **Writer / settlement** — подтверждения за интервал и всего, случаи нехватки средств, дубликаты и ошибки сохранения, последние результаты подтверждения.
6. **TX bot / нагрузка** — отправлено запросов, успешные ответы и ошибки, скорость отправки, задержка, число процессов и корутин, параметры запуска.

В каждой панели — компактная сводка **и небольшая лента последних событий**. Ошибка должна быть заметна сразу; обычное повторяющееся событие не должно занимать экран целиком. Подробные сведения по-прежнему можно оставить в отдельных логах или открыть специальным режимом.

**Confirmer — хорошее место для особенно наглядной панели.** Сейчас он раз в секунду запрашивает общее число узлов, выбирает случайную выборку максимум из 100 узлов и пересчитывает их веса с учётом потомков. Можно показать цикл как короткую прогресс-индикацию, например `выбрано 100 → обработано 97 → 3 ошибки`, рядом — общее число узлов, время цикла и компактное распределение рассчитанных весов. Важно честно подписывать выборку: это не полный пересчёт всего графа. Порог подтверждения `10`, максимальная глубина `7` и затухание `0.5` могут показываться как параметры алгоритма, а не как новые метрики.

# Техническое задание: презентационный live-терминал L0

## 1. Цель

Переработать визуальную подачу `./start`, чтобы запуск показывал живое состояние приложения в tmux: красиво, цветно и понятно как разработчику, так и гостю на демонстрации.

Это задача не на изменение бизнес-логики алгоритма, а на презентацию работы системы: структурированные статусы, счётчики, производительность, актуальные события и ошибки вместо сырых повторяющихся логов.

## 2. Исходный контекст

`./start` запускает шесть команд в tmux, используя раскладку `tiled`:

| Панель сейчас | Команда | Роль |
|---|---|---|
| Инфраструктурные логи | `make logs` | `docker compose logs -f` |
| API | `make api` | FastAPI на `127.0.0.1:8000` |
| Consumer | `make cons` | читает сообщения RabbitMQ и добавляет транзакции в граф |
| Confirmer | `make conf` | пересчитывает веса узлов графа |
| Writer | `make write` | сохраняет подходящие транзакции и обновляет балансы |
| Генератор | `make tx` | запускает `tx_bot.py` |

Сервисы `cons`, `conf`, `write` запускаются через `run.py`, который поддерживает перезапуск сервиса при изменении Python-файлов. Текущий вывод в основном имеет формат обычных INFO-логов. `tx_bot.py` пишет подробный JSON отправляемой транзакции и текст ответа целиком.

Полезные существующие параметры конфигурации в `src/config.py`:

- `CONFIRM_WEIGHT = 10`;
- `MAX_DEPTH = 7`;
- `DAMPING = 0.5`;
- confirmer пересматривает пул с паузой в одну секунду;
- writer проверяет пул с паузой 0,1 секунды.

## 3. Принятые продуктовые решения

- **Стиль:** премиальный тёмный терминал, умеренные акценты, без избыточного cyberpunk-декора.
- **Подача:** сводка и лента событий; подробности не нужно полностью удалять, но они не должны доминировать в основном виде.
- **Аудитория:** одновременно демонстрация и полезный оперативный экран для разработчика.
- **Данные:** допустимо добавить сбор метрик в сервисы и API, если это не меняет бизнес-поведение и не создаёт существенной нагрузки.

## 4. Требования к визуальной системе

1. Сохранить запуск через `./start` и tmux, включая возможность повторно подключиться к существующей tmux-сессии.
2. Оформить панели различимо: понятное название, короткий статус, осмысленный цветовой акцент.
3. Использовать единую палитру:
   - основной фон — тёмный, нейтральный;
   - активность и информационные акценты — cyan/голубой;
   - успех и здоровое состояние — зелёный;
   - предупреждение и деградация — янтарный;
   - ошибка и недоступность — красный;
   - второстепенные подписи — приглушённый серый.
4. Не окрашивать каждую строку случайным цветом: цвет должен кодировать состояние или важность.
5. Предусмотреть компактное отображение при изменении размера терминала. Панели не должны превращаться в нечитаемые обрезанные карточки; длинные значения нужно сокращать.
6. Если цвет недоступен или вывод перенаправлен, приложение не должно падать из-за управляющих ANSI-последовательностей.
7. Оформить tmux status line и рамки панелей в общей стилистике: названия панелей, визуальный фокус на текущей панели, короткая строка состояния сессии.
8. Не навязывать большое количество мигающей анимации. Допустима сдержанная индикация активности; интерфейс должен оставаться читабельным.

## 5. Содержимое панелей

### 5.1. Система и инфраструктура

Показывать состояние компонентов и процессов, насколько оно достоверно известно:

- API;
- RabbitMQ;
- MongoDB;
- Redis;
- Memgraph;
- время работы консоли или процесса;
- факт перезапуска сервиса, если он доступен.

Использовать явные состояния `UP`, `DOWN`, `UNKNOWN` или аналогичные. Не считать сервис здоровым только потому, что контейнер существует. Если достоверную проверку состояния без дополнительной настройки сделать нельзя, отображать `UNKNOWN`, а не выдуманный статус.

Сырые инфраструктурные логи не должны непрерывно занимать весь экран. Оставить в панели ограниченную ленту важных событий, особенно предупреждений и ошибок; подробный поток сохранить доступным через исходную команду/отдельный режим.

### 5.2. API

Показывать как минимум:

- общее количество запросов;
- текущую или скользящую скорость запросов;
- количество ответов `2xx`, `4xx`, `5xx`;
- последние события запроса;
- задержку запроса, если её можно собрать корректно.

Не выводить тела запросов и подписанные payload целиком. Добавление middleware или иной точки инструментирования допустимо, если сохраняются текущие HTTP-контракты и поведение обработчиков.

### 5.3. Consumer

Показывать:

- количество обработанных сообщений;
- количество успешно добавленных в граф транзакций;
- отказы с группировкой по доступным причинам: например, неверный формат, недостаток средств, дубликат, отсутствующий родитель, ошибка обработки;
- текущую скорость или число событий за короткий интервал;
- недавние события с коротким идентификатором транзакции.

Счётчики должны отражать реальные ветви обработки и подтверждение/отклонение сообщения, а не приблизительное число вызовов функции.

### 5.4. Confirmer

Показывать:

- общее число узлов графа;
- размер выборки для текущего цикла;
- число успешно обработанных узлов и число ошибок;
- длительность последнего цикла и время с его окончания;
- статистику весов только по фактически обработанным узлам текущей выборки: например, минимум/среднее/максимум или визуальное распределение;
- порог writer `CONFIRM_WEIGHT`;
- параметры алгоритма `MAX_DEPTH` и `DAMPING`;
- историю нескольких последних циклов в компактном виде, например короткой sparkline или полосой.

Обязательно отличать **общее число узлов** от **числа узлов, пересчитанных в выборке**. Текущая реализация выбирает не более 100 случайных узлов за цикл; интерфейс не должен выдавать выборочный пересчёт за пересчёт всего графа.

Не добавлять тяжёлый полный обход графа ради красивой метрики. По возможности собирать статистику из результатов уже выполняемого пересчёта и уже полученного общего числа узлов.

### 5.5. Writer

Показывать:

- подтверждённые транзакции за интервал и всего с момента старта;
- случаи недостатка средств;
- дубликаты;
- ошибки записи или компенсационного отката;
- количество транзакций, найденных выше порога, если это можно получить без дополнительного тяжёлого запроса;
- ленту последних действий с короткими хэшами и понятной меткой результата.

Не менять порядок операций сохранения MongoDB → Redis → Memgraph и существующую компенсационную логику ради телеметрии.

### 5.6. TX bot

Заменить печать полного JSON на компактное событие отправки:

- число отправленных запросов;
- успешные HTTP-ответы и ошибки;
- запросы в секунду или активность за интервал;
- задержка ответа, если её можно измерить;
- параметры запуска: число процессов и корутин, количество отправок;
- последние результаты с кратким HTTP-статусом и сокращённым идентификатором.

Не выводить полные транзакции, подписи и длинные тела ответов в основном экране. Для диагностики подробный вывод можно оставить отдельным явно включаемым режимом.

## 6. События, логи и точность метрик

1. Сохранить полезные ошибки и traceback в доступном разработчику виде.
2. Не генерировать повторяющиеся INFO-сообщения с периодичностью, которая засоряет экран. Регулярные сводки должны быть компактными и обновляться на месте либо публиковаться ограниченно.
3. Различать:
   - накопительные счётчики с момента старта;
   - значения за интервал;
   - значения одного цикла;
   - недоступные или неизвестные показатели.
4. Сокращать хэши для UI, сохраняя полный хэш в доступной диагностике, когда это действительно необходимо.
5. Не собирать и не показывать секреты, подписи, полные тела транзакций или чувствительные данные пользователей.
6. Добавленная телеметрия не должна менять результат обработки, подтверждение RabbitMQ-сообщений, условия подтверждения транзакций или REST-ответы.
7. При перезапуске сервиса явно сбрасывать либо маркировать его локальные счётчики, чтобы не создавать впечатление, будто они пережили перезапуск.

## 7. Предпочтительная реализация

Выбрать минимально сложную библиотеку или подход для терминального отображения, совместимый с зависимостями проекта. Перед добавлением зависимости проверить текущий `pyproject.toml`; не добавлять тяжёлый UI-фреймворк без необходимости.

Допустимы два варианта, итоговый выбор — за агентом:

- форматированные логи и обновляемые сводки в существующих панелях;
- отдельный компактный TUI/рендерер для панелей, если это устойчиво работает с текущим tmux-запуском.

В обоих случаях должны сохраниться простая диагностика, читаемые ошибки и возможность посмотреть детальные логи. Не строить визуализацию на дополнительных частых запросах полного графа или базы.

## 8. Что не менять

- бизнес-правила подтверждения и валидации транзакций;
- формат и смысл HTTP API;
- логику генерации родителей в `/pool`;
- порядок сохранения транзакции и механизмы компенсации;
- рабочую семантику `./start`, включая повторное подключение к существующей сессии;
- параметры `CONFIRM_WEIGHT`, `MAX_DEPTH`, `DAMPING` без отдельной необходимости.

## 9. Критерии приёмки

1. Запуск `./start` по-прежнему поднимает необходимые зависимости и открывает tmux-сессию.
2. Сохраняются все шесть ролей, но назначение и состояние каждой панели понятно без изучения исходного кода.
3. Основной экран не заполняют длинные JSON, подписи, полные хэши или повторяющиеся строки.
4. При успешной нагрузке видны живые изменения в API, consumer, confirmer, writer и TX bot.
5. Confirmer ясно показывает общее число узлов отдельно от размера обработанной выборки.
6. Ошибки и предупреждения визуально выделены, но подробности ошибки остаются доступными.
7. Недоступные метрики не подменяются догадками; для них отображается понятное неизвестное/неподключённое состояние.
8. Небольшой размер терминала и отключённые цвета не приводят к падению или полной потере читаемости.
9. Телеметрия не меняет обработку транзакций и не создаёт заметной дополнительной нагрузки.
10. Существующие тесты проходят; новые счётчики или middleware покрыты тестами хотя бы на основные события, статусы и сброс при перезапуске.
11. В документации описаны внешний вид панелей, клавиши/режим просмотра подробностей, если они добавлены, и способы отключить цвет или подробный режим.

**Вопросы, которые остались открытыми и для которых в ТЗ заложены безопасные значения по умолчанию:**

- Нужен ли отдельный клавишный режим для «сырого вывода» или достаточно оставить подробный просмотр через отдельную команду tmux? По умолчанию — оставить подробности доступными, не усложняя основной экран.
- Нужно ли хранить счётчики между перезапусками? По умолчанию — нет: показывать метрики с момента старта текущего процесса.
- Хотите ли отдельный визуальный мини-граф DAG? Это может стать хорошим вторым этапом, но в основной версии лучше ограничиться компактным распределением весов, чтобы не вводить дорогие запросы и не изображать граф условно.
