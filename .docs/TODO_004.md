# ТЗ: рекурсивный пересчёт score в confirmer

## Цель

Изменить расчёт score в `service/confirmer.py`, чтобы событие о новой транзакции из очереди `mid` запускало пересчёт score её родителей и родителей следующих уровней. Кандидаты, набравшие `score >= 1`, должны поступать в существующую очередь `out`.

Изменения в `service/writer.py` и `service/consumer.py` не нужны: writer продолжает слушать `out` и выполнять свою текущую логику, consumer — записывать транзакции в Memgraph и отправлять события в `mid`.

## Контекст и границы

Текущий confirmer обрабатывает событие `mid`, находит трёх родителей новой транзакции и отдельно для каждого вычисляет:

```text
score(parent) = internal_score(parent)
              + Σ internal_score(direct_child) / 3
```

Он учитывает только прямых детей и отправляет в `out` родителей, прошедших порог. Новый алгоритм должен учитывать потомков рекурсивно.

`CONFIRMS` направлено **от родителя к ребёнку**:

```text
(parent)-[:CONFIRMS]->(child)
```

Для перехода от новой транзакции к её родителям нужно обходить связи в обратном направлении.

`internal_score` рассчитывается consumer’ом и хранится в Memgraph. Score не следует записывать в Memgraph, Redis или другое хранилище: он рассчитывается для текущего события и используется для отбора кандидатов в `out`.

Все родители и дети, рассматриваемые расчётом, берутся из **текущего графа Memgraph**. Подтверждённые транзакции, уже удалённые из графа, в расчёт не входят. Родители-генезис, отсутствующие в графе, также не становятся кандидатами.

## Формула score

Для каждой транзакции `t` в графе:

```text
score(t) = internal_score(t)
         + Σ(score(child) / 3)
```

Сумма берётся по всем непосредственным детям `t` в Memgraph. Если детей нет, `score(t) = internal_score(t)`.

Следствия:

- `internal_score` транзакции добавляется один раз в её собственный score.
- Вклад каждого ребёнка передаётся родителю с коэффициентом `1/3`.
- Учитываются **все ветви поддерева** в графе, а не только ветвь, ведущая к транзакции текущего события `mid`.
- Если потомок влияет на предка через несколько путей DAG, его вклад учитывается через каждую ветвь. Это естественно следует из суммирования score непосредственных детей.
- Для DAG слияние путей не должно приводить к повторному добавлению `internal_score` самого узла в его score.

Иными словами, транзакция `mid` служит триггером пересчёта, но score каждого найденного предка — это полный score его поддерева в текущем графе.

## Глубина

Добавить в confirmer настройку:

```python
MAX_DEPTH: int | None = None
```

`None` — значение по умолчанию, означающее не ограничивать поиск предков: подниматься от триггера до всех достижимых корней графа.

Положительное целое значение ограничивает **только подъём от триггера к кандидатам**:

- прямые родители триггера — `DEPTH1`;
- их родители — `DEPTH2`;
- и так далее;
- кандидат включается, если он достижим не дальше заданной глубины.

Ограничение `MAX_DEPTH` **не ограничивает вычисление score**: score выбранного кандидата всегда рассчитывается по всему его поддереву в графе, до листьев.

При нескольких путях от триггера к одному предку узел должен быть включён в результирующий список не более одного раза. Для определения его уровня при заданном `MAX_DEPTH` использовать кратчайший путь от триггера.

## Загрузка графа и вычисление

На каждый валидный `mid` выполнить **один пакетный Cypher-запрос**, загружающий необходимую топологию всего текущего графа:

- hash каждой `Transaction`;
- `internal_score` каждой транзакции;
- hashes непосредственных родителей по существующим рёбрам `CONFIRMS`.

Результат запроса обработать в памяти:

1. Построить представление родительских и дочерних связей.
2. Найти предков триггера, проходя от транзакции по родительским связям, с учётом `MAX_DEPTH`.
3. Рассчитать score транзакций по графу снизу вверх, используя итеративную обработку DAG. Не использовать рекурсивные Python-вызовы, которые могут переполнить стек на длинной цепочке.
4. Сформировать список уникальных найденных предков со score.

Полная пакетная загрузка выбрана осознанно: она позволяет избежать множества Cypher-запросов и размножения строк при поиске всех путей в DAG. Допустимая сложность обработки одного события — `O(V + E)` по числу узлов и рёбер графа. Не выполнять N+1 запросы для отдельных родителей или детей.

В процессе расчёта ничего не записывать в Memgraph.

## Отбор и публикация

После расчёта:

- исключить из результата саму транзакцию-триггер;
- отобрать предков со `score >= 1.0`;
- каждого такого предка передать в существующий механизм публикации кандидата в `out` (`enqueue_candidate`);
- сохранить существующую дедупликацию через `queued:{hash}` и текущую обработку ошибок публикации;
- не публиковать один и тот же hash несколько раз в рамках одного события, даже если до него ведут несколько путей.

Порог остаётся `1.0`. Последующие проверки writer’а не изменять.

## Отсутствующие и некорректные данные

Если hash события `mid` отсутствует в графе, считать событие устаревшим: не вычислять score и не публиковать кандидатов — сохранить текущее поведение confirmer.

По принятому инварианту consumer не создаёт транзакции без числового `internal_score`: такая транзакция не должна попадать в граф. Не подменять отсутствующий или некорректный score нулём. Если при чтении обнаружено нарушение инварианта либо цикл в графе, не публиковать частичный результат; завершить обработку по принятой в confirmer политике ошибок.

## Что не входит в задачу

- Изменение writer, consumer, API, формата сообщений и логики `out`.
- Запись score или весов в Memgraph.
- Использование старого обхода потомков с `DAMPING`, обновлением `t.weight` или случайной выборкой узлов.

Указанный коммит `f3886f257862d499a84ba432bfee831d80e2895a` менял `src/utils/fn.py`; приведённый `_damping_case` и периодический пересчёт `weight` относятся к другой логике. Для этой задачи нужен не тот алгоритм, а описанное выше распространение score по DAG с делителем `3`.

## Проверки

Добавить или обновить тесты confirmer’а, покрывающие:

- score листа и цепочки из нескольких уровней;
- суммирование score всех непосредственных детей;
- независимые ветви поддерева, не проходящие через триггер;
- схождение DAG-путей: уникальный кандидат в результате и вклад по каждой ветви;

- отсутствие публикации дубликатов кандидата;
- один пакетный Cypher-запрос на событие и отсутствие записи в Memgraph;
