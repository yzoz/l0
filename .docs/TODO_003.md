# Техническое задание: событийное подтверждение транзакций по transfer score

## Цель

Заменить расчёт и хранение `weight` на событийную схему: после записи транзакции consumer уведомляет confirmer через `mid`; confirmer вычисляет score только для трёх родителей этой транзакции и отправляет подходящих кандидатов в `out`; writer обрабатывает кандидатов из очереди, а не сканирует Memgraph.

Это ТЗ предназначено для самостоятельной реализации. **Изменения кода в рамках текущей работы не выполнялись.**

## 1. Формула transfer score

В `src/utils/fn.py` уже находится реализация, которую нужно сохранить и использовать:

```python
alpha = 0.0005
beta = 0.5

def transfer_score(x, alpha, beta):
    return 1 - (1 + alpha * x) ** (-beta)
```

Сигнатуру, значения `alpha` и `beta` и формулу сохранить. Не перезаписывать существующие пользовательские изменения в этом файле.

Score транзакции `t` вычисляется **только по её прямым детям в Memgraph**:

```text
score(t) =
    transfer_score(amount(t), alpha, beta)
    + SUM(transfer_score(amount(child), alpha, beta) / 3)
```

В сумму входят непосредственные дети `t`, связанные с ней ребром `CONFIRMS`. Вклад каждого ребёнка делится на фиксированную константу `3` — число родителей транзакции. Не использовать конфигурационное значение или другой divisor.

**Не учитывать в формуле внуков и более дальние уровни**, не применять затухание по глубине. Score вычислять в памяти при обработке события; не сохранять в Redis, Memgraph, MongoDB или другом хранилище.

Кандидат проходит порог, если `score >= 1`.

## 2. Ровно три родителя

У каждой новой транзакции должно быть ровно три уникальных родителя:

- зафиксировать это валидацией модели/API с использованием `PARENTS = 3`;
- запросы с другим количеством родителей отклонять до публикации в `in`;
- сохранить проверку уникальности;
- обновить модельные, API- и интеграционные тесты, а также связанные клиентские контракты.

`/pool` уже возвращает три родителя, genesis использует три родителя; согласовать их с правилом и убедиться, что нигде не остаётся пути создания транзакции с другим количеством.

## 3. Очереди и направление обработки

Использовать три RabbitMQ-очереди:

| Очередь | Назначение | Payload |
|---|---|---|
| `in` | API → consumer | Существующий payload транзакции |
| `mid` | consumer → confirmer | Строка с `tx_hash`, без JSON-обёртки |
| `out` | confirmer → writer | Строка с `tx_hash`, без JSON-обёртки |

Существующую входную очередь `tx` переименовать в `in` во всех местах использования. Обновить связанные имена конфигурации и DLQ, например `tx.dlq` → `in.dlq`, и согласовать это с RabbitMQ provisioning и тестами. Очереди и сообщения должны сохранять используемый проектом механизм durable/persistent delivery.

### API

После проверки подписи API публикует транзакцию в `in`. В успешный ответ `/send/` добавить `tx_hash`, вычисленный тем же способом и по тем же данным, что использует consumer. Хэш должен быть идентичным хэшу, который вычислит consumer; это идентификатор транзакции, не статус и не гарантия её подтверждения.

### Consumer и `mid`

После успешной записи транзакции и её рёбер в Memgraph consumer публикует её `tx_hash` в `mid`. Confirmer использует Memgraph как источник истины: по хэшу читает транзакцию, её сумму и трёх родителей, затем пересчитывает score **только этих родителей**.

Новую транзакцию отдельно оценивать не нужно: её собственный `transfer_score` по заданной формуле ниже 1; согласно выбранному алгоритму кандидат должен получить вклад хотя бы одного потомка.

### Confirmer и `out`

Убрать случайную выборку и периодический обход пула. Confirmer должен потреблять `mid` и для каждого события:

1. Найти новую транзакцию в Memgraph по `tx_hash`.
2. Получить её родителей и суммы, необходимые для пересчёта.
3. Для каждого из трёх родителей вычислить текущий score по формуле из раздела 1, используя его непосредственных детей.
4. Если score родителя `>= 1`, отправить его хэш в `out`.
5. ACK-нуть событие `mid` после успешной обработки; при временной ошибке не подтверждать событие и обеспечить повторную доставку.

При параллельной обработке событий строгая сериализация по родителю не требуется. Каждый пересчёт читает актуальное состояние графа; целевое поведение — eventual processing актуального score без глобальной блокировки.

## 4. Доставка `mid` без потерь и без дублирования узла

Запись в Memgraph и публикация RabbitMQ не атомарны. Если запись транзакции прошла, а публикация в `mid` не удалась:

- consumer не должен ACK-ать сообщение из `in`;
- при повторной доставке consumer должен пересчитать тот же `tx_hash` и проверить наличие **этой же транзакции** в Memgraph;
- если в графе уже есть транзакция с тем же хэшем и соответствующими данными, consumer должен не создавать узел повторно, обеспечить корректность рёбер, повторно опубликовать `mid` и только после успешной публикации ACK-нуть `in`;
- повторные попытки не должны создавать дополнительные узлы или дублировать рёбра;
- конфликт существующего хэша с несовпадающими данными или конфликт уникальности `(credit, uniq)` не должен приводить к созданию второго узла; обработать его существующим путём ошибки/DLQ.

Проверить, что используемые Redis reservation/unique-маркеры и блокировки не заставят повторную доставку завершиться как обычный duplicate до выполнения recovery-пути.

## 5. Дедупликация `out` и lifecycle маркера

Использовать Redis-маркер `queued:{hash}`, чтобы ограничить дублирование кандидатов в `out`. Score в Redis не сохранять.

- Создавать маркер атомарно, например через `SET NX`, с lease/TTL.
- Публиковать в `out` только после успешного захвата маркера.
- Если публикация не удалась, освободить именно принадлежащий текущей попытке маркер и повторить обработку `mid`.
- Если процесс упал до публикации, истечение lease должно позволить повторную постановку.
- Если при повторной доставке события маркер ещё существует и нельзя установить, что публикация состоялась, не терять событие: дождаться освобождения/истечения lease или безопасно повторить обработку. Повторное сообщение допустимо; writer обязан быть идемпотентным.
- Writer очищает маркер после окончательного решения по кандидату либо после перевода его в deferred-состояние. Lease должен позволять восстановиться после остановки процесса.

Операции с маркером должны быть безопасны при истечении lease и повторном захвате; не удалять маркер, принадлежащий более новой попытке, если маркер хранит ownership token.

## 6. Writer

Заменить периодическое сканирование Memgraph обработкой `out`. Сохранить существующую логику финализации и проверок, если она не противоречит явно заданной ниже очередной обработке:

- проверки состояния родителей (`ok`, `pending`, `dead`);
- insufficient-funds проверку;
- Redis/MongoDB-операции подтверждения, включая confirmed marker с TTL;
- удаление подтверждённых узлов из Memgraph;
- каскадную обработку мёртвого поддерева;
- существующие блокировки writer и защиту от повторного подтверждения.

Удалить адаптивный порог writer, основанный на `POOL_SIZES` и `weight`. `POOL_SIZES` оставить только для подбора запаса родителей в `/pool`.

### Pending parents

Если кандидат из `out` не может быть подтверждён, потому что непосредственный родитель ещё pending:

- сохранить существующую семантику deferred-состояния;
- ACK-нуть текущее событие после успешного перевода в deferred;
- снять `queued:{hash}`;
- при подтверждении родителя повторно отправить его deferred-прямых детей в `out`, чтобы writer проверил их повторно без сканирования Memgraph.

Сбой при публикации повторных событий для детей должен обрабатываться как временная ошибка; не терять deferred-детей из-за неудачной публикации.

### Минимальный размер пула

Перед подтверждением writer проверяет количество транзакций в Memgraph:

- если `num_txs > PARENTS`, продолжить обычные проверки и обработку кандидата;
- если `num_txs <= PARENTS` (то есть не больше трёх), **ACK-нуть и отбросить это событие**;
- оставить транзакцию в Memgraph без изменения её состояния и без deferred-маркера;
- снять операционный `queued:{hash}` маркер, чтобы он не завис;
- не ставить кандидата на автоматическое ожидание до роста пула: это событие считается отвергнутым. Новая попытка возможна только если позднее придёт новое относящееся к нему событие.

Проверка нужна, чтобы сохранять в пуле минимум три кандидата для последующего выбора родительских транзакций клиентом. Это принятое поведение, даже если оно может привести к отсутствию повторного рассмотрения конкретного кандидата без нового события.

## 9. Критерии приёмки

1. `transfer_score` использует согласованные формулу, параметры и alpha/beta; тесты проверяют формулу и граничные значения.
2. Score учитывает только сумму самой транзакции и прямых детей; каждый вклад ребёнка делится на 3; более глубокие потомки не влияют.
3. Только три уникальных родителя проходят валидацию.
4. Consumer публикует plain-text `tx_hash` в `mid` после успешной записи транзакции и рёбер.
5. При сбое публикации в `mid` входное сообщение не теряется; повторная доставка повторно публикует событие без второго узла или повторных рёбер.
6. Confirmer обрабатывает только родителей из события, не сканирует пул и публикует в `out` только score `>= 1`.
7. Score не сохраняется ни в графе, ни в Redis, ни в другом хранилище.
8. Writer потребляет `out`, сохраняет существующие проверки и финализацию, не использует адаптивный весовой порог и не сканирует Memgraph по таймеру.
9. Deferred-прямой ребёнок повторно публикуется в `out` при подтверждении родителя.
10. При `num_txs <= 3` writer ACK-ает и отбрасывает событие, оставляя транзакцию и её состояние в графе без изменений и очищая только операционный queued-маркер.
11. Повторные сообщения и истёкшие lease не приводят к двойному подтверждению или зависшим queued-маркерам.
12. После миграции в Memgraph нет `weight`; старые весовые метрики, настройки и отображение удалены.
13. `/send/` возвращает `tx_hash`, совпадающий с хэшем, рассчитанным consumer.
14. Тесты покрывают успешный путь `in → Memgraph → mid → score → out → writer`, retries, дубли, pending-родителей, минимум пула и удаление legacy-веса.
