# ТЗ: алгоритм Rate Limit для допуска транзакций в Memgraph POOL

Версия 1.0 · Спецификация для агента-разработчика · Без реализации кода

## 1. Цель

Реализовать алгоритм ограничения скорости поступления новых транзакций в Memgraph POOL. Алгоритм должен ограничивать частоту попыток записи, обеспечивать равномерную подачу нагрузки в штатном режиме, поддерживать параллельное выполнение записей и позволять немедленно передавать освободившуюся возможность следующей транзакции при ошибке предыдущей записи.

Область задачи ограничена алгоритмом допуска транзакций. Необходимо разработать только логику rate limit, порядок допуска, управление временными слотами, обработку ошибок и ограничение параллелизма. Инфраструктуру, очереди, API, общую архитектуру приложения, Confirmer и Writer не изменять и не проектировать.

## 2. Исходные требования

| Параметр                   | Требование                                                                    |
| -------------------------- | ----------------------------------------------------------------------------- |
| Назначение                 | Ограничение частоты записи новых транзакций в POOL                            |
| Настройка                  | Положительное целое число TPS                                                 |
| Режим                      | Равномерный темп допуска                                                      |
| Порядок                    | FIFO — по времени поступления к лимитеру                                      |
| Первый допуск              | Немедленно, если есть ожидающая транзакция и свободная ёмкость                |
| Последующие допуски        | С интервалом \\(T = 1 / R\\), где \\(R\\) — заданный TPS                      |
| Параллельность             | Разрешена                                                                     |
| Ограничение параллельности | Максимальное число одновременно выполняющихся записей задаётся отдельно       |
| Успешная операция          | Memgraph успешно завершил добавление транзакции в POOL                        |
| Ошибка записи              | Немедленно передать освободившуюся возможность следующей ожидающей транзакции |
| Простой                    | Не накапливать пропущенные слоты и не наверстывать их всплеском               |
| Изменение TPS на лету      | Не входит в задачу                                                            |

## 3. Терминология

- Rate limit — алгоритм, определяющий допустимый момент начала попытки записи транзакции.
- TPS (`R`) — настроенный предел частоты допуска транзакций в секунду.
- Интервал (`T`) — минимальный штатный интервал между последовательными допусками: \\(T = 1000 / R\\) миллисекунд.
- Активная запись — транзакция, допущенная лимитером, но ещё не завершившая попытку записи.
- Слот — запланированная возможность начать запись в определённый момент времени.
- Освобождённая возможность — возможность немедленно начать следующую попытку после ошибки предыдущей записи. Она не должна приводить к нарушению выбранной политики скорости сверх явно разрешённого исключения.
- Ожидающая транзакция — транзакция, поступившая к лимитеру, но ещё не допущенная к записи.

## 4. Основной алгоритм допуска

### 4.1. Штатный режим

Алгоритм должен соблюдать следующие правила:

1. Транзакции рассматриваются в порядке поступления к лимитеру.
2. Если ожидающих транзакций нет, алгоритм не выполняет никаких действий.
3. Если появляется первая ожидающая транзакция, свободная ёмкость параллельного выполнения позволяет её обработать, а лимитер не занят ожиданием обязательного временного слота, транзакция допускается немедленно.
4. После допуска следующая штатная возможность назначается на время предыдущего допуска плюс \\(T\\).
5. Когда наступает назначенное время, следующая транзакция допускается, если она ожидает обработки и не превышен предел параллелизма.
6. Если параллельных записей уже максимально допустимое число, новые записи не запускаются до освобождения ёмкости.
7. Если временной слот наступил, но ёмкости нет, лимитер не должен создавать дополнительную возможность допуска сверх установленной скорости.
8. После простоя пропущенные временные слоты не накапливаются. При появлении новых транзакций обработка продолжается с обычным интервалом, без компенсационного всплеска.

### 4.2. Пример штатной работы

При `TPS = 100` интервал составляет 10 мс.

| Время | Действие                                            |
| ----- | --------------------------------------------------- |
| 0 мс  | Первая транзакция допускается сразу                 |
| 10 мс | Следующая транзакция допускается, если есть ёмкость |
| 20 мс | Следующая транзакция допускается, если есть ёмкость |
| 30 мс | Следующая транзакция допускается, если есть ёмкость |

Время завершения записи не определяет расписание штатных допусков: если запись длится 35 мс, следующая транзакция всё равно может быть допущена на своём временном слоте, если свободна ёмкость параллельного выполнения.

## 5. Ограничение параллельного выполнения

Лимитер должен поддерживать отдельный параметр `MAX_IN_FLIGHT` — максимальное количество одновременно выполняющихся записей.

Требования:

- `MAX_IN_FLIGHT` должен быть положительным целым числом.
- Новая транзакция не может быть допущена, если число активных записей достигло лимита.
- Успешное завершение или ошибка записи освобождает одну единицу активной ёмкости.
- Освобождение ёмкости само по себе не должно приводить к неконтролируемому запуску нескольких ожидающих транзакций.
- Если одновременно наступили временной слот и освобождение ёмкости, допускается не более одной новой транзакции в рамках одной возможности допуска.
- После завершения записи обработчик должен корректно обновить состояние лимитера, не теряя и не дублируя возможности допуска.

## 6. Обработка успешной записи

Успехом считается только успешное завершение операции добавления транзакции в Memgraph POOL.

После успеха алгоритм должен:

1. Уменьшить число активных записей на единицу.
2. Зафиксировать успешное завершение соответствующей попытки.
3. Освободить ёмкость параллельного выполнения.
4. Продолжить обработку ожидающих транзакций в соответствии с FIFO и расписанием лимитера.
5. Не допускать повторного списания одной и той же возможности или повторного завершения одной попытки.

Успешное завершение не должно автоматически запускать следующую транзакцию раньше разрешённого временного слота только потому, что запись завершилась быстро.

## 7. Обработка ошибки записи

По результатам согласования выбрана политика C: при ошибке немедленно допустить следующую транзакцию, даже если равномерный темп временно нарушится.

При ошибке записи алгоритм должен:

1. Уменьшить число активных записей на единицу.
2. Освободить соответствующую ёмкость параллельного выполнения.
3. Если есть ожидающая транзакция, немедленно передать ей освободившуюся возможность допуска, не ожидая следующего штатного слота.
4. Сохранить FIFO-порядок: возможность получает первая ожидающая транзакция.
5. Не запускать больше одной следующей транзакции на одну освобождённую возможность.
6. Если ожидающих транзакций нет, не сохранять возможность для последующего компенсационного всплеска.
7. После внепланового допуска восстановить штатное расписание без накопления пропущенных временных слотов.

Важное следствие: политика C допускает временное превышение номинальной частоты `TPS`. Поэтому `TPS` в этой спецификации — штатная скорость допуска, а не абсолютная математическая верхняя граница при ошибках. Агент не должен одновременно обещать строгий предел в любых условиях и реализовывать немедленную выдачу освобождённой возможности.

## 8. FIFO и справедливость

Порядок поступления к лимитеру является единственным критерием очередности.

Требования:

- Более поздняя транзакция не может обойти более раннюю ожидающую транзакцию.
- Временные слоты не должны изменять порядок транзакций.
- Ошибка записи не даёт приоритета самой ошибочной транзакции для немедленного повторного запуска: освободившуюся возможность получает следующая ожидающая транзакция.
- Если транзакции поступили практически одновременно, порядок определяется фактическим порядком регистрации лимитером.
- Если входная транзакция отклонена другими проверками до поступления к лимитеру, она не участвует в его FIFO-порядке.

## 9. Параметры и валидация

Алгоритм должен принимать следующие параметры:

| Параметр           | Требование                                               |
| ------------------ | -------------------------------------------------------- |
| `TPS`              | Положительное целое число                                |
| `MAX_IN_FLIGHT`    | Положительное целое число                                |
| Часы               | Монотонные, не зависящие от коррекции системного времени |
| Временной интервал | \\(T = 1 / TPS\\) секунды                                |

При некорректных значениях `TPS` или `MAX_IN_FLIGHT` реализация должна выдавать явную ошибку конфигурации, а не переходить к неограниченной обработке.

Расписание должно использовать монотонное время, чтобы изменение системных часов не приводило к повторным слотам, пропускам или неконтролируемым всплескам.

## 10. Критерии корректности

Реализация считается соответствующей ТЗ, если выполняются все следующие условия:

1. Первая транзакция после простоя допускается сразу, если нет иных ограничений.
2. В штатном режиме последующие транзакции допускаются с заданным интервалом.
3. При медленной записи параллельные операции допускаются по расписанию до достижения `MAX_IN_FLIGHT`.
4. Число активных записей никогда не превышает `MAX_IN_FLIGHT`.
5. Порядок допуска соответствует FIFO.
6. Успешное завершение записи не создаёт дополнительного разрешения на досрочную запись.
7. Ошибка записи освобождает ёмкость и при наличии ожидающих транзакций вызывает немедленный допуск следующей.
8. После простоя не происходит компенсационного всплеска.
9. Одно событие завершения не может освободить ёмкость дважды.
10. Временные расчёты не зависят от системного wall-clock времени.
11. Алгоритм не теряет и не дублирует ожидающие транзакции вследствие собственных переходов состояния.
12. Поведение на границах временных слотов детерминировано и покрыто тестами.

## 11. Обязательные тестовые сценарии

| Сценарий                                    | Ожидаемый результат                                         |
| ------------------------------------------- | ----------------------------------------------------------- |
| Первая транзакция после запуска             | Немедленный допуск                                          |
| Очередь заполнена, записи быстрые           | Допуск по штатному расписанию                               |
| Запись дольше временного интервала          | Следующие записи допускаются параллельно, пока есть ёмкость |
| Достигнут `MAX_IN_FLIGHT`                   | Новые записи не запускаются до освобождения ёмкости         |
| Успешная запись до следующего слота         | Нет внепланового допуска                                    |
| Ошибка записи при наличии очереди           | Следующая транзакция допускается немедленно                 |
| Ошибка записи при пустой очереди            | Освободившаяся возможность не накапливается                 |
| Длительный простой                          | Нет компенсационного всплеска                               |
| Одновременные завершения нескольких записей | Корректный учёт освобождённой ёмкости и FIFO                |
| Повторное событие завершения                | Нет двойного освобождения ёмкости                           |
| Изменение системных часов                   | Расписание лимитера не нарушается                           |
| `TPS = 1`                                   | Штатный интервал равен одной секунде                        |
| Некорректные параметры                      | Явная ошибка конфигурации                                   |

## 12. Что необходимо проверить перед принятием реализации

Есть один принципиальный момент, который агент должен явно отразить в документации и тестах: политика немедленного допуска после ошибки несовместима с гарантией «не более N транзакций в любой секунде». Она также может приводить к коротким всплескам, если ошибки происходят часто.

Поэтому итоговая реализация должна обеспечивать именно согласованную модель:

- равномерное расписание как штатный режим;
- ограничение параллелизма;
- немедленный допуск после ошибки как явно разрешённое исключение;
- отсутствие накопления разрешений во время простоя.

Если впоследствии понадобится абсолютный верхний предел TPS без исключений, политику C потребуется заменить на возврат ёмкости без досрочного допуска либо дополнить отдельным строгим ограничителем.

Итог для агента: реализовать алгоритм, соответствующий разделам 1–11, не меняя инфраструктуру или архитектуру системы. Код должен быть покрыт тестами на штатные интервалы, параллельность, FIFO, ошибки и временные границы.
