**Алгоритм (точный, рабочий, под наш кейс)**

### Token Bucket с непрерывным пополнением (самый чистый вариант)

**Параметры (статические):**
- `R` = RATE_LIMIT_TPS          // целевая средняя скорость
- `B` = RATE_LIMIT_BURST         // максимальный бурст (ёмкость ведра)
- Обычно `B` ставят 1.5–3× от `R` (например R=200, B=400–600)

**Состояние (в памяти consumer'а):**
- `tokens` — текущее количество токенов (float64)
- `last_refill` — timestamp последнего пополнения (монотонные часы, nanoseconds)

**Инициализация:**
```
tokens = B
last_refill = now()
```

**Перед каждой успешной записью user-tx в Memgraph:**

1. Вычисляем, сколько времени прошло:
   ```
   now = monotonic_now()
   elapsed = now - last_refill
   ```

2. Пополняем токены:
   ```
   tokens += elapsed * R
   if tokens > B:
       tokens = B
   last_refill = now
   ```

3. Пытаемся взять токен:
   ```
   if tokens >= 1.0:
       tokens -= 1.0
       // разрешаем запись в Memgraph
       return ALLOW
   else:
       // токенов нет
       return DENY (или WAIT)
   ```

### Как именно ждать (критично)

Два нормальных варианта (выбираем один):

**Вариант A — Блокирующее ожидание внутри consumer'а (проще и чище для одного инстанса)**  
Пока `tokens < 1` — consumer просто `sleep` на короткое время (1–5 мс) и снова проверяет.  
Сообщение из Rabbit уже взято (ack позже, после успешной записи).  
Плюсы: просто, latency предсказуема, не дёргаем Rabbit.  
Минусы: один consumer занимает поток/горутину, пока ждёт.

**Вариант B — Возврат сообщения в очередь (nack + requeue или publish в delay-очередь)**  
Если токенов нет — делаем nack с requeue=true (или кидаем в delay-очередь на 10–50 мс) и берём следующее сообщение.  
Плюсы: consumer никогда не блокируется.  
Минусы: чуть больше нагрузки на Rabbit, возможны небольшие нарушения порядка.

**Рекомендация сейчас:** Вариант A (блокирующий wait).  
Он проще, предсказуемее и при одном consumer'е почти всегда лучше. Потом легко перейти на B, если понадобится горизонтальное масштабирование.

### Важные тонкости (чтобы не обосраться)

- Использовать **монотонные часы** (не wall clock), иначе при NTP-скачках будет хуйня.
- `tokens` хранить как `float64`, пополнять непрерывно — это даёт гораздо более гладкое поведение, чем дискретные тики.
- Запись в Memgraph происходит **только** после успешного взятия токена. Если запись упала — токен **не** возвращаем (иначе можно превысить лимит при ретраях).
- Все остальные проверки consumer'а (подпись, хэш, валидация и т.д.) делаются **до** попытки взять токен. Токен берём в самом конце, прямо перед записью.

### Как будет выглядеть поведение

- Нагрузка < R → токены почти всегда полные, latency минимальная.
- Короткий всплеск ≤ B → проходит сразу (бурст).
- Длительная перегрузка → consumer начинает равномерно "капать" со скоростью ≈ R, очередь Rabbit растёт.
- После спада нагрузки consumer быстро разгребает накопившееся (пока есть токены).
