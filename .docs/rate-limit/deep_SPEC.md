# ТЗ: Rate limiter в consumer'е — ограничение впуска транзакций в Memgraph

## 1. Контекст и цель

В системе есть пайплайн: клиент → API → очередь → **consumer** → Memgraph (POOL, DAG). Memgraph — самое узкое место. Другие микросервисы (`confirmer`, `writer`) тоже пишут/читают Memgraph, но **вне скоупа этой задачи** — их не трогаем и не лимитируем.

**Цель:** ограничить скорость впуска новых транзакций из consumer'а в Memgraph до `N` транзакций в секунду, чтобы ограничить число узлов, одновременно находящихся в Memgraph. Транзакции, не прошедшие гейт, **не теряются** — они остаются в очереди (Kafka/брокер), а worker consumer'а приостанавливает вычитку, пока не появится разрешение (backpressure).

**Обоснование `N` (Little's law):** при стабильном среднем времени жизни узла в Memgraph `W_avg` (определяется writer'ом/TTL — вне нашего кода) потолок числа узлов `C_max` связан с темпом впуска как `N = C_max / W_avg`. `N` задаётся **константой в конфиге**, подобранной вручную один раз по этой формуле. Никакой runtime-адаптации, никакой связи с writer'ом, никакого пересчёта на лету — **не требуется**.

## 2. Скоуп

**В скоупе:**
- Один in-process rate limiter внутри consumer'а.
- Алгоритм: **fixed window**.
- Семантика: **block** (backpressure внутри процесса, сообщения не теряются, не ack'аются, пока не обработаны).
- Порядок в worker'е: **acquire → poll** (сначала разрешение, потом сообщение из брокера).

**Вне скоупа (НЕ реализовывать):**
- Мультиинстанс-координация. Каждый процесс consumer'а независим, свой `N`, свой счётчик. Итоговый кластерный потолок = `N × K` (K — число инстансов) — принимается как известный риск.
- Redis, распределённые счётчики, лидер-выборщик.
- Hot reload `N` (без рестарта). `N` читается один раз при старте.
- Режим «наблюдение» (count-only). Лимитер всегда активен.
- Refund/возврат токена при ошибке записи в Memgraph. Токен сгорает при успешном `acquire`, независимо от исхода записи.
- Дедупликация по хешу транзакции.
- Per-client / per-user квоты. Все транзакции равны.
- Приоритеты транзакций. Строгий FIFO на уровне очереди, гейт однородный.
- Anti-starvation (max-age / max-wait). При block-семантике не нужно.
- Учёт latency Memgraph, queue depth, любые адаптивные метрики как триггеры.
- Изменения в API, брокере, схеме Memgraph, writer'е, confirmer'е.

## 3. Архитектурное размещение

- Гейт — **одна точка** в consumer'е, перед обработкой каждой транзакции (перед вычиткой из брокера, см. §5).
- Один экземпляр лимитера на процесс consumer'а.
- Worker'ы consumer'а — пул потоков. Все они обращаются к **общему** состоянию лимитера (мьютекс + condvar).

## 4. Состояние лимитера (per-process)

```
struct RateLimiter {
    int N;                       // из конфига, tx/s, фиксировано на старте
    int permits;                 // доступные разрешения в текущем окне
    time_point window_start;     // монотонное время начала окна
    mutex mtx;
    condition_variable cv;
}
```

- `permits` инициализируется в `N` при старте.
- `window_start` инициализируется текущим монотонным временем.
- Источник времени — **строго монотонные часы** (`std::chrono::steady_clock` в C++, `time.monotonic()` в Python, `System.nanoTime()` / `Instant` с `Clock` монотонным в Java и т.п. — в зависимости от стека). Системное время (`Wall clock`) **запрещено** — NTP-скачки сломают окно.

## 5. Алгоритм

### 5.1. Окно

- Длина окна — **ровно 1 секунда** (`N` tx/s).
- Окна идут **строго последовательно** от монотонного времени: `[t0, t0+1)`, `[t0+1, t0+2)`, ...
- Сброс `permits` в `N` происходит при переходе в новое окно.

### 5.2. Тикер (фоновый поток)

Отдельный фоновый поток (или таймер), запускается при инициализации лимитера:

```
loop:
    sleep(tick_interval)                    // tick_interval = 50–100 мс
    lock(mtx)
    if (now >= window_start + 1.0s):
        // сдвигаем window_start на целое число секунд вперёд
        // (если тикер проспал несколько окон — пропускаем их, не накапливая)
        k = floor((now - window_start) / 1.0s)
        window_start += k * 1.0s
        permits = N
        cv.notify_all()
    unlock(mtx)
```

- Пропущенные окна (если тикер проспал) **не накапливаются** — просто сдвиг на `k` окон вперёд, `permits = N`. Никакого «`permits += N*k`».
- `notify_all` — чтобы разбудить всех спящих worker'ов для перепроверки условия.
- Тикер не завершается, пока живёт лимитер.

### 5.3. `acquire()` — блокирующий вызов worker'а

```
acquire():
    lock(mtx)
    while (permits == 0):
        cv.wait(mtx)                  // спим, Kafka не поллим, ничего не берём
    permits -= 1
    unlock(mtx)
    // возврат: разрешение получено, теперь можно идти в брокер
```

- При `permits == 0` worker **спит на condvar** — это и есть backpressure: брокерская очередь растёт, ничего не теряется, ничего не ack'ается.
- Никаких таймаутов ожидания, никакого «если долго ждали — пустить всё равно». Ждём до появления permit'а.
- Пробуждение — только от тикера (при сбросе окна). Spurious wakeups обрабатываются циклом `while`.

### 5.4. `release_if_unused()` — возврат permit'а, если сообщение не взяли

После `acquire()` worker идёт в брокер. Если сообщение **не получено** (очередь пуста, poll вернул пусто):

```
release_if_unused():
    lock(mtx)
    permits += 1
    // notify_one() — разбудить одного спящего, т.к. permit вернулся
    cv.notify_one()
    unlock(mtx)
```

- Это **не** refund после ошибки записи. Это возврат «неиспользованного авансом взятого» permit'а, если worker сходил за сообщением, а его не оказалось.
- Если сообщение получено — permit **не возвращается** (сгорел), независимо от исхода обработки (успех/ошибка записи в Memgraph).

### 5.5. Цикл worker'а

```
loop:
    limiter.acquire()                 // блокирует, если permits == 0
    msg = broker.poll(timeout = short) // например, 100–500 мс
    if (msg == null):
        limiter.release_if_unused()   // вернуть permit, продолжить цикл
        continue
    try:
        process(msg)                  // проверки + запись в Memgraph
        broker.ack(msg)
    catch:
        broker.nack(msg) / ошибка     // permit НЕ возвращается
```

## 6. Свойства и границы

- **Средняя пропускная способность:** ровно `N` tx/s за длинный интервал.
- **Boundary burst:** на стыке окон возможно до `2N` за очень короткий промежуток (все N в конце окна + все N в начале следующего). **Принято осознанно.** Никаких мер против этого (никакого token bucket, GCRA, случайного сдвига окна) — не реализовывать.
- **Потери:** нет. Транзакция либо получает permit и обрабатывается, либо остаётся в брокере.
- **Мультиинстанс:** каждый процесс независим. Кластерный потолок = `N × K`. Документировать в README/комментарии, что при масштабировании `N` на процесс надо уменьшать, если нужен стабильный общий потолок.
- **Монотонность времени:** гарантируется выбором монотонных часов; скачки системного времени не влияют.

## 7. Конфигурация

- `N` — целое положительное, tx/s.
- Источник: конфиг-файл / env-var (на усмотрение стека; зафиксировать в README сервиса).
- Читается **один раз при старте** процесса. Hot reload не нужен.
- Валидация: `N > 0`, иначе — ошибка старта.
- В лог при старте: `rate_limiter_initialized N=<N>`.

## 8. Метрики (обязательны все)

Все метрики — per-process. Формат/бэкенд — по стеку проекта (Prometheus/OTel/что принято).

| Метрика | Тип | Описание |
|---|---|---|
| `rate_limiter_acquired_total` | counter | Успешных `acquire()` |
| `rate_limiter_rejected_total` | counter | **Всегда 0** в block-режиме; оставить для будущего, если режим поменяется |
| `rate_limiter_delayed_total` | counter | Сколько раз `acquire()` уходил в `wait()` (факт блокировки) |
| `rate_limiter_wait_seconds` | histogram | Время, проведённое в `acquire()` (включая 0 для мгновенных) |
| `rate_limiter_tokens_available` | gauge | Текущее `permits` в окне |
| `rate_limiter_current_rate` | gauge | Текущее `N` |

`delayed_total` и `wait_seconds` — единственный способ увидеть, что лимитер реально срабатывает и consumer упирается. Без них система «работает», но непонятно, где потолок.

## 9. Логирование

- Старт: `rate_limiter_initialized N=<N>`.
- Никаких per-transaction логов (шумно). Только метрики.
- На переходе окна — не логировать (слишком часто). Только метрики.

## 10. Тесты (обязательный минимум)

1. **Пропускная способность:** при `N=100` за 10 секунд успешных `acquire()` ровно `≈1000` (±boundary burst). Проверить на длинном интервале, не на границе окна.
2. **Block-семантика:** при `permits=0` вызов `acquire()` блокируется, не возвращается до сброса окна.
3. **Сброс окна:** после `window_start + 1.0s` `permits` становится `N`, все спящие просыпаются.
4. **Возврат permit'а:** `acquire()` → `release_if_unused()` → `permits` вернулся; следующий `acquire()` не блокируется.
5. **Сгорание permit'а:** `acquire()` → обработка (успех или ошибка) → permit **не** вернулся.
6. **Пропуск окон:** если тикер проспал 2 окна, `permits = N` (не `2N`).
7. **Конкурентность:** M worker'ов одновременно вызывают `acquire()`, суммарно за окно не более `N` успешных.
8. **Валидация конфига:** `N <= 0` → ошибка старта.
9. **Монотонность:** симуляция скачка системного времени не влияет на окна (тест на уровне выбора часов / абстракции времени).

## 11. Критерии готовности

- [ ] Лимитер реализован в consumer'е, единая точка входа перед poll'ом брокера.
- [ ] Fixed window, 1 секунда, монотонные часы.
- [ ] Block-семантика: worker спит на condvar при исчерпании, брокер не поллится.
- [ ] Возврат permit'а при пустом poll'е.
- [ ] `N` из конфига, читается один раз, валидируется.
- [ ] Все 6 метрик экспортируются.
- [ ] Все 9 тестов зелёные.
- [ ] В README/комментарии зафиксировано: boundary burst до 2N допустим; кластерный потолок = `N × K`; refund/дедуп/приоритеты/per-client квоты/hot reload — сознательно вне скоупа.
