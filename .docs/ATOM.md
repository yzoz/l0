## TL;DR

Твоя гипотеза **верна по существу, но пропускает один слой**: genesis-деньги существуют в системе **дважды** — и это первопричина. Плюс всплывает смежный баг с `credit=""`, который пока **маскирует** двойную запись. Если починить одно, не трогая другое — второе разыграется. Ловушка «по адресам» опасна (поймает чужие транзакции); ловушка должна быть «по природе транзакции» (минт vs перевод). Атомарность в `_confirm` от такого вмешательства **не ломается**, если трогать только Redis-инкремент, а порядок Mongo→Redis→Memgraph сохранить.

## 1. Точная карта цепочки

| Шаг | Где | Что происходит |
|---|---|---|
| `make genesis` | `genesis.py:74-104` | Очистка Mongo (`txs.drop()`), `FLUSHALL` Redis, очистка Memgraph. Затем 3 `TxStore` кладутся **в Memgraph** как `:Transaction` (`weight=1.0`) и **в Redis** `SET balance:{debit} = amount` (абсолютное значение) |
| `make tx` | `tx_bot.py` → API → Rabbit → `consumer.py:60` | Обычные транзакции; `parents` берутся из `/pool` |
| ingress | `consumer.py:99-194` | `check_duplicate` (Mongo) → `verify_balance` (`get_balance(credit)`) → `verify_parents` → `add_to_graph` (узел + рёбра `CONFIRMS` от **неподтверждённых** родителей, проверка цикла) |
| веса | `confirmer.py:67` | `weight = 1.0 + Σ damping^depth · own_weight` потомков (до `MAX_DEPTH=7`); при `weight ≥ CONFIRM_WEIGHT=10` узел «созрел» |
| settlement | `writer.py:101` `check_pool` | Достаёт зрелые узлы (`LIMIT 100`), для каждого: lock `writer:{hash}` → если `confirmed:{hash}` есть, пропуск → **`get_balance(tx.credit)`** → если `balance < amount` — удалить узел → иначе `_confirm` |
| confirm | `writer.py:45` `_confirm` | **1.** Mongo `insert_tx` (источник истины) → **2.** Redis pipeline `INCRBY balance:{debit}` + `DECRBY balance:{credit}` + `SET confirmed:{hash}` → **3.** удалить узел из Memgraph. Компенсация: упал Redis → `delete_one` из Mongo |

Ключевой факт: **genesis создаётся напрямую в `genesis.py`, минуя Rabbit/consumer**. Значит «ловушка» живёт целиком в `writer.py`.

## 2. Нейминг `get_balance` — там не две функции

Реально есть **одна функция чтения + одна функция расчёта + мёртвый параметр**:

- **`get_balance_sync(addr, db)`** — `src/utils/profile.py:8`. Источник истины: агрегат MongoDB (`$facet` income/outcome → `debit` это получатель, `credit` это плательщик → `income − outcome`). Несмотря на суффикс `_sync`, она **`async def`**. Здесь «sync» означает «синхронизировано с **реестром (Mongo)**», а **не** «синхронная функция».
- **`get_balance(addr, db, redis, sync=False)`** — `src/utils/profile.py:35`. Кэш-first: читает Redis `balance:{addr}`; на промахе считает через `get_balance_sync` (Mongo) и **делает backfill `SET`** в Redis.
- **Параметр `sync=True`** — это **не вторая функция**, а переключатель внутри `get_balance`, который просто делегирует в `get_balance_sync`, минуя кэш.

**Важное наблюдение:** `sync=True` **не используется нигде в проде**. Греп по всему проекту находит только `sync=False` в тестах (`tests/tb.py:22`, `tests/test_balances.py:24`); прод-вызовы (`writer.py:124`, `consumer.py:106`, `api/schema.py:79`) идут со значением по умолчанию `sync=False`. То есть `sync=True` — мёртвый/отладочный хвост.

**Почему это сбивает с толку:** слово «sync» перегружено в двух разных смыслах («читать из Mongo» и «переключатель кэша»). Плюс `_sync` на async-функции врёт о конкурентности.

*Направление переименования (для обсуждения):* `get_balance_sync` → что-то вроде `balance_from_ledger` / `compute_balance_mongo`; параметр `sync=` → `no_cache=` либо выкинуть совсем (он мёртвый). Это чисто косметика, но она убирает путаницу, пока мы лезем в логику балансов.

## 3. Где реально двойная запись (твоя гипотеза + числа)

Genesis-деньги представлены **двумя разными механизмами одновременно**:

1. **Абсолютный pre-load:** `genesis.py:103` `SET balance:{debit} = amount`.
2. **Сам genesis как транзакция** в Memgraph, которая позже пройдёт нормальный путь подтверждения и в `_confirm` сделает **относительный** `INCRBY balance:{debit} amount` (`writer.py:74`).

Возьмём адрес `A1 = 9ui23…`, `amount = 500_000_000_000_000` (5·10¹⁴).

**Сценарий B — двойная запись (то, чего ты боишься):**
- после `make genesis`: Redis `balance:A1 = 5·10¹⁴`.
- genesis «дозрел» → `_confirm` вставляет его в Mongo и делает `INCRBY balance:A1 5·10¹⁴`.
- итог: **Redis `balance:A1 = 10¹⁵` (2X)**, а Mongo-реестр содержит genesis ровно один раз → `get_balance_sync(A1) = 5·10¹⁴`.
- **Redis ≠ Mongo. Удвоение.** Твой страх подтверждается как латентный баг.

## 4. Попутный баг, который пока маскирует удвоение: `credit=""`

У всех трёх genesis-транзакций **`credit=""`** (плательщика нет — это минт). А `check_pool` **до** `_confirm` делает (`writer.py:124`):

```
balance = get_balance(tx.credit, ...)   # = get_balance("")
if balance < tx.amount:  →  удалить узел, не подтверждать
```

`get_balance("")` читает ключ `balance:` (с пустым суффиксом) → после `FLUSHALL` его нет → backfill из Mongo → `0`. Значит `0 < 5·10¹⁴` → **genesis отклоняется как «недостаточно средств» и удаляется, так и не попав в Mongo.**

**Сценарий A — фактическое поведение сейчас:**
- Redis `balance:A1 = 5·10¹⁴` (pre-load остался).
- genesis **удалён**, в Mongo его нет → `get_balance_sync(A1) = 0`.
- **Redis ≠ Mongo (5·10¹⁴ против 0).** Деньги-«призрак» живут только в кэше, в реестре их нет.

**Почему это важно для тебя:** сейчас удвоение (B) скорее всего **не проявляется**, потому что genesis **не доходит** до `_confirm` — его сначала режет проверка баланса из-за `credit=""`. Но стоит тебе «просто убрать» эту проверку, чтобы genesis проходил, — и тут же включится удвоение (B). **Поэтому ловушка обязана закрывать две вещи сразу:** и пропуск проверки credit-баланса для genesis, и подавление `INCRBY/DECRBY`. Иначе чиним одно — разбудим другое.

## 5. Инвариант, на котором стоит вся проверка согласованности

Тесты `tests/tb.py` и `tests/test_balances.py` проверяют ровно одно:

> **Redis `balance:{addr}` == `get_balance_sync(addr)` (Mongo-реестр)** для genesis-адресов.

Правильное конечное состояние для `A1` (сценарий C — цель):
- Redis `balance:A1 = 5·10¹⁴` (pre-load **сохранён**, не тронут),
- Mongo: genesis-запись есть (`debit=A1, amount=5·10¹⁴`) → `get_balance_sync(A1) = 5·10¹⁴`,
- **Совпадают.** И реестр полон, и кэш корректен.

Значит фикс обязан сделать **два действия одновременно**: (а) довести genesis до Mongo, (б) **не** дать genesis изменить pre-load в Redis. Оба — иначе инвариант не сойдётся.

## 6. Разбор «сложной атомарности» в `_confirm` — что страшно, а что нет

Порядок `writer.py:45-99`: **Mongo insert → Redis pipeline → удалить узел**, с компенсацией (упал Redis → `delete_one` из Mongo).

**Что атомарно (бояться нечего):**
- Redis `pipeline()` в redis-py по умолчанию — это `MULTI/EXEC`. То есть `INCRBY + DECRBY + SET confirmed` применяются **атомарно** относительно других клиентов. Хорошо.

**Что НЕ атомарно (реальные окна):**
1. **Mongo ↔ Redis не транзакционны.** Падение процесса *между* insert и pipeline оставит транзакцию в Mongo без обновлённых балансов. Компенсация ловит только **исключение** Redis, но **не смерть процесса**. Окно ничем не закрыто.
2. **`TTL = 360` у `confirmed:{hash}`** (`config.py:16`). Маркер подтверждения живёт 6 минут. После истечения `verify_parents`/`add_to_graph` (`consumer.py:125,159`) могут не найти `confirmed:{parent}` и попытаться построить ребро к уже удалённому узлу. Дубликат, приехавший после TTL, отсечётся `check_duplicate` по `(credit, uniq)`, но не по hash. Тонкость на границе.
3. **TOCTOU «проверил–потом списал».** Баланс читается в `check_pool`, а уменьшается через `DECRBY` позже. Lock'и — `writer:{hash}` и `consumer:{hash}` — **по хэшу транзакции, а не по адресу**. Две транзакции с одного адреса могут обе пройти проверку и обе списаться → овердрафт. Внутри одного writer-цикла это приглушено последовательностью, но consumer читает баланс конкурентно.
4. **Абсолютный `SET` против относительного `INCRBY/DECRBY`.** genesis и backfill в `get_balance` пишут абсолют; writer — относительные дельты. Смешение обоих типов обновлений одного ключа — классический источник расхождений при гонках.

**Вывод по атомарности:** твоя «страшная атомарность» локально — это Redis-pipeline + компенсация. Ловушка, которая **пропускает только `INCRBY/DECRBY` для genesis**, порядок Mongo→Redis→Memgraph и компенсацию **не трогает**: для genesis Redis-шаг сводится к единственному `SET confirmed` (атомарно), Mongo insert остаётся первым, узел удаляется последним. Атомарность сохраняется.

## 7. Почему ловушка «по адресам» опасна

Если сделать «если `tx.debit ∈ DEV_ADDR` — не инкрементить», ты поймаешь **не только genesis**, а **любую обычную транзакцию, которая платит В адрес** `DEV_ADDR`. Каждый вход денег на генезис-адрес потерял бы начисление (`INCRBY balance:{debit}`) → деньги исчезали бы.

Правильный дискриминатор — **не адрес, а природа транзакции: минт (создание денег) vs перевод (перемещение)**. Структурно минт = `credit == ""` (плательщика нет; модель `Tx` валидирует только `debit` как ключ и `debit ≠ credit`, а `credit` — свободная строка, `src/models/tx.py:55-61`). Варианты маркера минта: `credit == ""` (самый честный структурный), либо явный флаг `is_genesis` / отдельное поле, либо `msg == "genesis"` (хрупко — `msg` юзер-контролируемый, `MaxLen 10`).

**Где ставить:** обе точки — в `writer.py`:
- **`check_pool` (строка 124):** для минта **пропустить** проверку `get_balance(tx.credit)` (иначе `credit=""` всегда режет).
- **`_confirm` (Redis-шаг, строки 73-77):** для минта выполнить **только `SET confirmed`**, без `INCRBY/DECRBY`. Mongo insert — оставить (ради полноты реестра и `get_balance_sync`), удаление узла — оставить.

Consumer трогать не нужно — genesis через него не проходит.

## 8. Варианты решения (без кода, для выбора)

**Вариант A — «Минт-исключение в writer» (я за него).** Распознать минт в writer: пропустить credit-проверку, вставить в Mongo, **не** трогать `balance:*` (сохранить pre-load), но поставить `confirmed`, удалить узел. Минимальный срез, атомарность цела, инвариант Redis==Mongo сходится.

**Вариант B — «Genesis предподтверждён».** Не класть genesis в Memgraph вообще: сразу Mongo insert + `SET balance` + `SET confirmed`. Модель чище (нет окна «genesis в ожидании»), **но** убивает корневые узлы DAG, к которым цепляются рёбра `CONFIRMS` и от которых идёт набор веса. Меняет механику подтверждения — рискованно.

**Вариант C — «Убрать pre-load, считать из реестра».** Удалить `SET balance` из genesis, положиться на `get_balance_sync`. Ломает игру: пока genesis не подтверждён, у адресов баланс 0 и все траты режутся на ingress. Не годится.

**Вариант D — гибрид A + жёсткий маркер минта.** Как A, но вместо неявного `credit == ""` завести явный признак минта (в данных genesis), чтобы ловушка была надёжной и не зависела от пустой строки.
